Security Gates & VEX

DevSecOps 실무 마스터: VEX 가이드

소프트웨어 자산 명세서(SBOM)의 한계를 깨고, 실제 서비스 악용 가능성을 중심으로 보안 위협을 현명하게 통제하는 표준 지침서

💡 1. SBOM의 한계와 VEX의 탄생

소프트웨어 공급망 보안을 지키기 위해 우리는 모든 오픈소스 라이브러리와 컨테이너 OS 구성 요소를 기재한 SBOM (Software Bill of Materials)을 생성합니다. 그러나 정밀 스캐너를 돌려 SBOM 취약점을 추적하기 시작하면 심각한 문제가 발생합니다.


"포함은 되어 있지만, 실제 공격 경로로 작동할 수 없는 무해한 취약점"들까지 기계적으로 차단 경보를 올려 빌드를 마비시키기 때문입니다. 이를 보안 업계에서는 '오경보 피로(False Positive Fatigue)'라고 부르며, 이를 유연하고 체계적으로 극복하고자 VEX(Vulnerability Exploitability eXchange) 표준이 개발되었습니다.

🚪 직관적인 일상 비유: "어느 비상구 문고리의 고장"

어느 대형 빌딩의 인테리어 리모델링 과정에서 벽으로 완전히 막혀 폐쇄된 옛날 비상구 문이 있습니다. 이 문의 손잡이가 고장 났습니다.

  • 일반 스캐너 (SBOM 기반): "이 빌딩에 고장 난 비상구 문(취약점)이 있습니다! 안전 규정 위반이므로 빌딩 출입(배포)을 금지합니다!"
  • VEX 문서의 외침: "그 문은 지난달 공사로 두꺼운 콘크리트 벽 뒤에 묻혀서 누구도 접근하거나 열 수 없는 문입니다. 그러므로 이 손잡이 고장은 빌딩 안전에 아무런 영향을 주지 않습니다. 출입을 승인합니다."

🔄 2. SBOM vs VEX 비교 분석

두 문서 규격은 대립 관계가 아닌, 공급망 보안을 완성하기 위해 상호 보완하는 동반자 관계입니다.

📦 SBOM (CycloneDX / SPDX) 정적 자산 식별
  • 목적: 소프트웨어를 구성하는 원재료(라이브러리명, 버전, 파일 해시) 목록 나열
  • 스캔 기준: 특정 패키지가 시스템에 "물리적으로 존재하는가?"
  • 한계점: 실제 호출 여부나 보안 장비에 의한 보호 조치 반영 불가
  • 기록 주체: 빌드 자동화 도구 및 패키지 분석 엔진
🛡️ VEX (Vulnerability Exploitability) 실질 위험도 판별
  • 목적: 발견된 개별 취약점(CVE)이 런타임 환경에서 "악용 가능한가?" 증명
  • 판단 기준: 실행 가능 여부 및 완화(Mitigation) 조치 반영
  • 장점: 불필요한 보안 차단 오경보를 제거하여 개발 가용성 확보
  • 기록 주체: 제조사 개발팀, 보안 담당자, 취약점 분석가

📊 3. VEX의 4대 핵심 상태 (Core Status)

VEX 국제 표준 규격(CSAF, CycloneDX)에 명시된 취약점 판정 기준 4가지를 인터랙티브 탭을 클릭하여 자세히 알아보세요.

Not Affected

취약점이 포함된 패키지가 존재하는 것은 팩트이나, 분석 결과 우리 애플리케이션 환경에서는 절대 악용될 수 없음이 증명된 상태입니다. 이 상태를 선언할 때는 반드시 표준화된 정당화 사유(Justifications)를 함께 문서화해야 보안 감사를 통과할 수 있습니다.

component_not_present : 취약한 기능이 포함된 하위 모듈이나 클래스가 실제 빌드 결과물에 포함되지 않음.
vulnerable_code_not_present : 원본 라이브러리는 취약하나 우리 소스에서 커스텀 패치를 적용하여 해당 취약 코드가 이미 제거됨.
vulnerable_code_not_in_execute_path : 취약한 모듈을 로드하지 않거나 해당 코드를 호출하는 동작 시나리오가 아예 존재하지 않음.
inline_mitigation_already_exist : 네트워크 방화벽, 프록시 설정, 혹은 내부 필터에 의해 해당 취약점 공격 페이로드가 원천 차단됨.
Affected

취약점이 라이브러리에 존재하고, 실제 런타임 공격 경로 상에서 호출 또는 악용될 수 있는 직접적인 위험이 확인된 상태입니다.

* 후속 조치: 즉시 패치 버전을 적용하거나, 즉각적인 조치가 어렵다면 사용자에게 일시적 우회 방안(예: 특정 설정 비활성화)을 보안 권고사항으로 제공해야 합니다.

Fixed

이전 빌드에서는 취약점이 활성화되어 있었으나, 이번 빌드 및 릴리즈 버전에 취약점이 수정된 상위 버전의 라이브러리나 패치를 성공적으로 결합했음을 공표하는 상태입니다.

* 주요 용도: 보안 규제 기관이나 고객사에게 이전 보안 이슈가 정상적으로 릴리즈 라이프사이클 내에서 완결(Resolve)되었음을 소명할 때 기재합니다.

Under Investigation

취약점이 스캔에서 탐지되었으나, 우리 코드에 유해한 영향을 미치는지 분석을 시작했거나 아직 결론을 내리지 못한 상태입니다.

* 중요성: 무조건적인 보안 차단(Build Fail)을 임시 보류시키고 정상 동작시키면서, 보안 팀에게 정밀 위협 분석을 할 수 있는 버퍼 시간(Buffer Time)을 벌어주는 역할을 합니다.

🛠️ 4. Grype 실무 연동 & VEX 스펙 문서의 실체

VEX 공식 규격은 보안 시스템이 파싱해야 하므로 복잡한 JSON-LD/XML 형태로 되어 있습니다. 아래는 경량 VEX 표준인 OpenVEX의 실제 원본 규격 예시입니다.

OpenVEX 공식 JSON 스펙 예시
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://my-company.com/vex/doc-12345",
  "author": "Security Engineering Team",
  "timestamp": "2026-07-10T10:00:00Z",
  "statements": [
    {
      "vulnerability": { "name": "CVE-2023-45678" },
      "products": [ { "@id": "pkg:maven/com.example/backend-app@1.0.0" } ],
      "status": "not_affected",
      "justification": "vulnerable_code_not_in_execute_path",
      "impact_statement": "The vulnerable XML parsing features are completely disabled in our spring boot configuration."
    }
  ]
}

🎯 젠킨스 및 Grype 보안 파이프라인에서의 현명한 대안

매번 위와 같은 복잡한 규격 문서를 손수 편집하는 것은 개발자 입장에서 부담스럽습니다. 따라서 Grype 취약점 스캐너는 프로젝트 폴더 내에 심플한 .grype.yaml 선언형 설정 파일을 심어두면, 해당 설정값을 VEX Not Affected 명세서로 자동 매핑해 주는 강력한 편의성을 제공합니다.

Grype 스캐너 VEX 선언 파일 (.grype.yaml)
# .grype.yaml
# 프로젝트 루트 디렉토리에 위치하면 grype 스캔 시 자동으로 오경보 취약점을 바이패스합니다.
ignore:
  # 1. OS 기본 패키지 취약점 예외 처리 (우회 프록시나 가상 방화벽으로 차단된 경우)
  - vulnerability: CVE-2022-37434
    reason: "Accepted OS package risk. Vulnerable function not used in runtime environment."
  
  # 2. WAS(톰캣 등) 런타임 관련 무해 취약점 예외 처리
  - vulnerability: CVE-2023-46589
    reason: "Mitigated by nginx reverse proxy in production environment."

⚙️ 5. VEX 기반 DevSecOps 실무 운영 흐름

VEX를 실무 파이프라인에 적용하여 무결점 배포에 성공하는 실제 업무 흐름은 다음과 같습니다.

1단계: 코드 커밋 및 푸시
개발자가 소스코드 또는 Docker 빌드 설정을 변경하여 Git Repository에 푸시합니다.
2단계: CI 파이프라인 작동 & 보안 품질 게이트 작동
Jenkins가 작동하여 grype --fail-on high를 실행합니다. 새로 탐지된 위험 취약점이 있을 경우 빌드를 자동으로 거부(FAILURE)합니다.
3단계: 영향력 분석 및 VEX 기재 (현재 진행 단계)
보안팀과 개발자가 실패 로그를 살펴본 후, 'Not Affected'가 확실한 항목을 식별해 .grype.yaml 파일에 우회 등록합니다.
4단계: Git 재푸시 및 배포 성공
VEX 설정이 탑재되어 재푸시된 코드는 Grype 예외 처리기 덕분에 빌드를 녹색불(SUCCESS)로 통과하고, 최종적으로 Dependency-Track에 SBOM 등록과 배포에 성공합니다.
